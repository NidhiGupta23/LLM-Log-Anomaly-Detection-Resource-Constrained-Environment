# LLM Benchmarking in Resource-Constrained Environments

## Overview

This project evaluates and compares the performance of multiple Large Language Models (LLMs) under resource-constrained environments for log analysis tasks. The goal is to understand how lightweight and distilled models perform when applied to real-world system logs and industrial datasets.

The models evaluated in this study include:

- RAPID (from DSBA-Lab)
- DeepSeek-R1-Distill-Qwen-1.5B
- Qwen3-4B
- Qwen2.5-0.5B-Instruct
- Llama-3.2-3B-Instruct

These models are tested on below dataset commonly used in log analysis and anomaly detection:

- BGL (Blue Gene/L)

The final outcome is a comparative analysis focusing on accuracy, efficiency, and suitability for deployment in constrained environments (e.g., limited GPU/CPU, memory, or edge devices).


## Objectives

- Benchmark multiple LLM-based log analysis approaches
- Evaluate trade-offs between model size and performance
- Measure inference latency, memory usage, and throughput
- Assess accuracy in anomaly detection and log parsing tasks
- Identify models suitable for edge or low-resource deployment

## Datasets

### BGL (Blue Gene/L)
The experiments use the BGL dataset, a widely used benchmark dataset for log anomaly detection. BGL contains system logs generated by the Blue Gene/L supercomputer and provides labels that distinguish normal and abnormal events.
Two principal evaluation workloads were used:
- 500 logs
- 5000 logs

The larger workload was used to investigate how execution time, throughput, memory usage, and classification performance change as the number of processed logs increases.
The dataset is highly imbalanced towards normal logs. For this reason, the study places particular emphasis on F1 score, precision, recall, and confusion-matrix results, rather than relying on accuracy alone.


## Experimental Approaches
1. Zero-Shot Prompting
In zero-shot evaluation, models receive instructions describing the anomaly-classification task but no labelled examples. The model is asked to classify each log as:

- 0 = Normal
- 1 = Abnormal
Different maximum-output-token limits were evaluated to determine whether generation length affected classification behaviour and execution performance.

2. Few-Shot Prompting
Few-shot prompting provides labelled BGL examples before the log being classified. Five compositions of four examples were evaluated, including combinations such as:
- four normal logs
- four abnormal logs
- two normal and two abnormal logs
- three abnormal and one normal log
- one abnormal and three normal logs

The experiments also varied the maximum generation length such as 10, 25, 50, 75 and 100 tokens. 
This stage investigates:
- normal/abnormal example balance
- maximum-token limits
- output-format consistency
- false-positive and false-negative behaviour
- model-specific response patterns

3. Fine-Tuning
Selected models were fine-tuned using labelled BGL data to adapt them directly to binary log anomaly classification. Fine-tuned models were subsequently evaluated using several inference-prompt configurations to study whether prompt length and structure continued to influence classification performance and computational cost. Fine-tuning produced the strongest and most consistent classification results in the final evaluation.

4. GGUF Quantized Inference
Fine-tuned models were evaluated using GGUF quantized variants suitable for local CPU inference. The two primary formats were:

- Q4_K_M — approximately 4-bit mixed quantization, prioritising smaller model size and reduced memory consumption.
- Q8_0 — approximately 8-bit quantization, retaining greater numerical fidelity at the cost of a larger model.
The comparison investigates whether quantization can reduce deployment requirements while maintaining strong anomaly-detection performance.

## Metrics

### Classification Performance
The main classification metrics are:
- True Positives (TP)
- True Negatives (TN)
- False Positives (FP)
- False Negatives (FN)
- Accuracy
- Precision
- Recall
- F1-score
- Confusion Matrix
Because the BGL evaluation data are imbalanced, F1-score and confusion matrix behaviour are particularly important for determining whether a model genuinely distinguishes normal and abnormal events.
A model that predicts every log as normal can still obtain high accuracy, while a model that predicts every log as abnormal can achieve very high recall. Neither represents reliable anomaly detection.

### Runtime Performance
Runtime measurements include:
- Total execution time
- Average latency per log
- P95 latency
- P99 latency
- Throughput
- Percentile throughput

### Resource Usage
The experiments additionally record, where applicable:
- CPU time
- Average CPU cores used
- RAM usage
- Peak RAM usage
- Model size
- Prompt-token usage
- Completion-token usage
These metrics allow classification performance to be evaluated together with computational cost.

## Methodology

1. Preprocess datasets into a unified format
2. Apply each model to:
   - Log parsing
   - Anomaly detection
3. Standardize prompts across models where applicable
4. Run inference under identical hardware constraints
5. Collect performance and resource usage metrics
6. Compare results across models and datasets

### Key Findings

The experiments produced several important observations:
- Model size alone did not determine anomaly-detection performance
- The largest evaluated model did not consistently produce the strongest classification results.
- Qwen3.5 showed severe single-class prediction behaviour in several zero-shot and few-shot configurations, whereas the substantially smaller Qwen2.5 model achieved the strongest overall results after task adaptation.

### Fine-tuning produced the most reliable improvement

Fine-tuning substantially improved classification performance and output consistency compared with prompting alone.
Among the evaluated LLMs, Qwen2.5-0.5B-Instruct provided the strongest overall trade-off between anomaly-detection performance and computational efficiency. Its small parameter count allowed it to achieve strong classification results while requiring less CPU time and memory than the larger evaluated models.

### Quantization retained strong performance

Both Q4_K_M and Q8_0 quantized variants retained strong classification performance after fine-tuning. The formats presented different trade-offs:
- Q4_K_M generally reduced model size and memory requirements.
- Q8_0 retained greater numerical fidelity and produced slightly stronger or faster results in some configurations.

### Hardware capacity primarily affected runtime
Equivalent deterministic model configurations produced the same classification outputs across the 8-GB and 16-GB CPU VMs in the evaluated comparisons. The major differences were instead observed in:
- total execution time
- throughput
- CPU time
- resource utilisation

### Larger workloads substantially increased processing cost
Increasing the workload from 500 to 5,000 logs caused a substantial increase in execution time and CPU time. Peak RAM usage increased much less because memory consumption was influenced primarily by the loaded model and inference configuration.

### Comparison with RAPID Framework

The final evaluation compares fine-tuned Qwen2.5 with RAPID. The results reveal a trade-off between classification quality and computational efficiency:
1. Fine-tuned Qwen2.5
 - higher precision
 - higher F1-score
 - fewer false-positive alerts
 - stronger overall balance between normal and abnormal classification

2. RAPID Framework
 - substantially faster execution
 - considerably smaller model footprint
 - perfect abnormal-class recall in the reported comparison

Therefore, Qwen2.5 was identified as the strongest LLM-based approach, while RAPID remained advantageous when speed, compactness, and complete anomaly recall were prioritised
